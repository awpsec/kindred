# Browser sign-in and verification

Bot browser profiles are persistent and screen-specific, both on a hosted server and in a standalone VM. Existing Chromium launches do not disable password saving. The user can accept the browser's Save password prompt; bots may use normal masked autofill from the installed password manager or the browser's built-in password manager for the verified service/account. Bot guidance is manager-neutral: focus the login field, select a matching saved login from the autofill popup, and inspect the manager or browser's autofill controls when no inline suggestion appears. Password-manager unlocking and revealed-secret screens stay with the user. Do not inspect/export credential stores. Per-screen profiles are not a security boundary against privileged tools in the shared VM or its host.

The operating guide directs bots encountering an expired session to try the authorized saved login, then request human help rather than silently treating an inaccessible inbox as empty. Existing user-action notifications respect notification and mute preferences. This is a response to an observed login failure, not a background session-expiry detector.

`request_user_action` accepts optional `authentication` metadata:

- `service`: display name (required)
- `method`: `signin`, `sms`, `email`, `authenticator`, `push`, or `security_key` (required)
- `destination`: the observed masked delivery detail, if present
- `code_length`: exact observed character count (4–16), omitted when unknown; the UI uses one accessible input rendered as individual slots
- `submission`: `enter` (default) or `automatic` for sites that submit on code entry

Code methods render a masked 4–16 character alphanumeric field. The bot focuses the real website code field and observes the page before requesting help. The UI stays in chat and sends input to `/api/user-tasks/{id}/code`. The endpoint checks the pending task, bot, run, method, absence of manual control and code format under the screen lease. A durable attempt marker prevents repeated delivery, including after uncertain failures. It sends text to the guest without a model tool event, database code storage, or returned guest output. Browser requests and guest process memory necessarily carry the input transiently. No code is added to chat or a draft. Never log request bodies at a reverse proxy.

Submitting a code types into the prepared field, presses Return unless automatic submission was specified, and readies the existing task for resumption. The bot must observe the resulting page before continuing; submission does not prove successful authentication. Sites may render entered codes on the screen, so the private route prevents text/history disclosure but cannot promise that a website will never display a code. Manual takeover remains available when needed. Push/security-key methods retain the human handoff without a code input. Expired/cancelled tasks cannot accept input. An uncertain delivery error leaves the task paused and requires checking the screen; the same request cannot inject a code twice. A rejected/expired code can get a fresh handoff request after the current step is resolved.

Validation uses backend task-boundary tests and WebKit/Chromium UI fixtures. It does not establish acceptance by any live service or encrypted password-store behavior on every guest image.

## Managed launch and recovery

Guest URL opening, desktop Browser/New window and startup restoration use one launch policy. Screen 1 keeps `/home/bot/.local/share/kindred/browser`; screens 2–32 keep their existing `browser-N` directories. The policy selects the same-UID Openbox process for that exact display, checks its executable/start identity and owned live session-bus socket/private runtime directory, and refuses ambiguous or unavailable context. Existing profile directories must remain owned, private and unredirected. Refusal leaves them intact; it is not evidence that the website signed the user out.

All three entrypoints request session restoration and an ephemeral loopback-only attachment endpoint. A URL or new-window request may be forwarded to an already running Chromium instance. Its original process, encryption backend and startup flags stay in force; there is no forced browser restart or endpoint adoption. The guest embeds the same launcher source, so its URL path works after a verified runtime update even before separately installed scripts are updated.

Managed runtime maintenance stages the shared launcher and dependent desktop/startup scripts from compiled source, accepts only known previous managed bytes or the exact candidate, and verifies their returned hashes separately from the runtime receipt. Customized or redirected scripts fail before the runtime switches. The helper is installed first; caught replacement failures restore switched scripts. A private nonblocking lock rejects concurrent installations. Existing browsers and profile data are not installation targets. An abrupt process/host termination between individual file replacements can leave a partial compatible script set; a later verified maintenance attempt must reconcile it. This is not a transactional filesystem or reboot guarantee. Manual installations need the matching deployment files, not just a new executable.

The launch policy does not set `--password-store=basic`, replace keyrings, export credentials or migrate cookie databases. Chromium chooses its Linux password store based on the environment and can fall back when the selected store is unavailable; consistent bus access alone cannot prove that an existing encrypted store is readable. See [Chromium's Linux password-storage documentation](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/linux/password_storage.md). Existing locked/unavailable keyrings need diagnosis and the user's normal unlocking flow, not a plaintext workaround.

Recovery starts with the assigned browser and observed account state. Distinguish a profile/desktop access error from an expired website login. For an observed sign-in page, verify the origin/account and try matching masked saved-login autofill once; an absent inline suggestion is not proof that no login exists. Request help for an observed locked vault, failed/missing matching login or human-only verification. Do not bypass MFA/CAPTCHA or retry a rejected sign-in indefinitely.

`tools/test-browser-launch.py` checks ownership/context refusal and isolation. `tools/test-browser-entrypoints.py` executes the real shell and embedded-helper entrypoints in a disposable network-none container using command captures. `tools/test-browser-persistence.cjs` uses actual headed Chromium/Openbox/DBus with isolated XDG/profile paths and a synthetic loopback server: HttpOnly persistent/session cookies, localStorage, IndexedDB and restored tabs survive normal close, a crash and a verified runtime/desktop update; another screen has none of that state. These fixtures do not establish encrypted-keyring readability, a VM reboot, OS/package upgrade, or real Google/Venmo authentication.

## Preserve session cookies during restarts and updates

The installed Debian Chromium 154 fixture reproduced session-cookie loss after a clean browser close and desktop restart, despite `--restore-last-session`; cached Chrome for Testing 153 retained the same synthetic session cookie. Persistent cookies, localStorage and IndexedDB survived in both. A persistent directory and restored tabs alone therefore do not prove persistent authentication.

Dedicated guests install `/etc/chromium/policies/managed/browser-session.json` with `RestoreOnStartup: 1`, Chromium's supported "restore last session" policy. [Chromium documents that this also preserves session-only cookies across exit](https://chromium.googlesource.com/chromium/src/+/HEAD/components/policy/resources/templates/policy_definitions/Startup/RestoreOnStartup.yaml). It applies to the bot computer's Chromium, including browser launches outside the dock. It does not edit cookie databases, extend website expiration times, disable encryption, or copy the owner's browser profile. The session cookie remains a session cookie. Other managed policies or administrator customizations require reconciliation rather than silent replacement.

Both desktop service units run `stop-browser.py` before stopping X11/DBus. The helper requests normal window closure only for the exact same-UID Chromium parent, profile and display, then waits for it to exit and save. It neither kills unrelated browsers nor sends a forced kill when a close is refused or times out. An unsaved-work dialog can still block a clean close; systemd's outer shutdown deadline remains in force. Managed Reboot sends ACPI shutdown, waits for the existing VM process to stop, then boots the same disk. A timeout leaves the computer running and reports the failed shutdown; it never substitutes a hardware reset.

Runtime maintenance verifies, backs up and stages the shutdown helper, desktop units and session policy alongside the existing launch scripts. It reloads unit definitions without restarting running desktops. Failed verification or a caught switch/reload failure retains the runtime and restores switched files. A customized policy file is preserved and fails before switching. Existing version-matched runtime/launcher files remain part of the verified receipt.

`tools/test-installed-browser-persistence.py` runs against installed guest Chromium with a disposable profile/display and a synthetic loopback server. Before the policy, session cookies were absent after restart; after the repair, persistent and session cookies, localStorage and IndexedDB survive recreation of both X11 and DBus, with a normal browser exit and the same profile inode. `tools/test-browser-stop.py` covers exact process/profile selection and refusal, and the updater/reboot suites cover retained data, rollback, idempotence and shutdown timeout behavior. These checks do not authenticate to a real website or reboot an owner VM.

Websites retain their own security policies. [Venmo documents additional checks for unrecognized devices/browsers](https://help.venmo.com/cs/articles/login-security-vhel151), and [Google may reject automated or embedded browser sign-ins](https://support.google.com/accounts/answer/7675428?hl=en). Preserved local state cannot promise that those services will accept or retain a session.
